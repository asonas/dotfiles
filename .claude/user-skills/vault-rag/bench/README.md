# vault-rag 検索品質ベンチ

`/vault-rag` が依存している qmd の検索品質を、質問と正解ファイルの組で測るための装置です。設定やインデックスをいじったあとに回して、体感ではなく数字で効果を確認します。

## 実行

```sh
ruby verify-fixture.rb                                        # 先にfixtureの健全性を検査する
qmd bench vault-fixture.json                                  # 15問 x 4バックエンド、3〜4分
qmd bench vault-fixture.json --json > /tmp/bench-new.json     # 記録して比較に使う

ruby report.rb /tmp/bench-new.json                            # type別の内訳を見る
ruby report.rb baseline-2026-07-26.json /tmp/bench-new.json   # ベースラインとの差分
```

`baseline-2026-07-26.json` が現行の基準値です。施策を入れたら差分を取り、README の測定履歴に追記してください。改善が確認できたら新しい baseline として置き換えます。

`verify-fixture.rb` は次を検査します。ここを通さずに bench を回すと、fixture の不備を検索性能の劣化と読み違えます。

- `expected_files` が vault に実在するか。空白や括弧を含むファイル名は1文字ずれても静かにスコア0になる
- 各クエリに `lex:` と `vec:` の両方があるか。**`lex:` が無いと bm25 バックエンドは空を返してスコア0になる**（`bench.js` が構造化クエリから lex 行だけを拾う実装のため）
- `expected_files` がコレクション相対のフルパスか。qmd の `pathsMatch` はサフィックス一致なので、`G4.md` のようなベース名だけだと別ファイルに誤爆する

## fixture の構成

15問。type ごとに集計されるので、施策がどの層に効いたかが分かります。

| type | 問数 | 正解の層 | 何を測るか |
|---|---|---|---|
| topical | 5 | wiki | 概観質問で派生レイヤの要約ページが出るか |
| alias | 2 | wiki | frontmatter の `aliases` 経由で引けるか |
| exact | 3 | 一次ソース | 固有名詞やエラーメッセージからの直接ヒット |
| semantic | 3 | 一次ソース | 質問の語彙とノートの語彙がずれている場合 |
| cross-domain | 2 | 一次ソース + wiki | 同一トピックが複数ノートに割れている場合 |

`/vault-rag` は「wiki で概観 → 一次ソースに降りる」2層構造を前提にしているので、topical と alias が wiki を引けているかが実質的な健康診断です。

## 測定履歴

### 2026-07-26 ベースライン

`full`（BM25 + ベクトル + LLMリランキング）が `/vault-rag` の実際の経路です。

| backend | R@1 | R@3 | MRR |
|---|---|---|---|
| bm25 | 0.667 | 0.667 | 0.683 |
| vector | 0.067 | 0.500 | 0.328 |
| hybrid | 0.600 | 0.833 | 0.711 |
| **full** | **0.600** | **0.900** | **0.733** |

type 別（full）:

| type | R@1 | R@3 | MRR |
|---|---|---|---|
| alias | 0.500 | 0.500 | 0.500 |
| cross-domain | 0.000 | 0.750 | 0.417 |
| exact | 0.667 | 1.000 | 0.833 |
| semantic | 1.000 | 1.000 | 1.000 |
| topical | 0.600 | 1.000 | 0.733 |

### 2026-07-26 運用ファイル除外（施策A）の効果

`wiki/log*.md` と `wiki/index.md`（計107KB、111チャンク）を qmd の ignore に入れた前後の比較。`~/.config/qmd/index.yml` の ignore を一時的に外して再インデックスし、同じ fixture を回して測定。

R@3 の変化:

| backend | before | after | 差 |
|---|---|---|---|
| bm25 | 0.667 | 0.667 | ±0 |
| vector | 0.500 | 0.500 | ±0 |
| hybrid | 0.833 | 0.833 | ±0 |
| **full** | **0.800** | **0.900** | **+0.100** |

type 別 R@3（full）:

| type | before | after | 差 |
|---|---|---|---|
| topical | 0.800 | 1.000 | +0.200 |
| cross-domain | 0.500 | 0.750 | +0.250 |
| exact / semantic / alias | 変化なし | | ±0 |

**効いたのはリランキング段だけ**という結果でした。log.md と index.md は vault 中で最も固有名詞の密度が高いため、BM25 とベクトルの素の順位では上位3件に食い込まないものの、**リランカーへ渡す候補枠を占有して高いスコアを得ていた**（実測例: G4 の質問で log.md 0.44 / index.md 0.38 が本命の wiki/G4.md 0.36 を上回っていた）。`/vault-rag` が使うのは `full` の経路なので、この改善はそのまま体感に効きます。

影響が topical と cross-domain に集中したのも整合的で、これらは wiki ページを正解とする質問です。運用ファイルが同じ wiki ディレクトリの中身を要約している以上、競合するのは当然でした。

### 2026-07-26 wiki専用コレクションによる2段検索（施策C）: 不採用

`/vault-rag` の「wiki で概観 → 一次ソースに降りる」をプロンプトの指示ではなく検索経路として実装する案を検証し、**採用しないことに決めた**。以下は再検討するときのための記録。

計測した2方式と、topical / alias（wiki ページが正解の7問）の結果:

| 構成 | topical R@3 | topical MRR | alias R@3 |
|---|---|---|---|
| `asonas` コレクションのみ（現行） | 1.000 | 0.733 | 0.500 |
| `asonas-wiki` コレクションを追加 | 1.000 | 0.800 | 0.500 |
| wiki 専用の独立インデックス（`--index wiki`） | 1.000 | 0.800 | 0.500 |

**この計測では優劣を判定できなかった**。topical R@3 はベースラインの時点で既に 1.000、つまり天井に張り付いており、飽和した指標の上では改善を検出しようがない。R@1 は 0.600 のまま（5問中3問なので1問の増減で ±0.200 動く）、MRR は +0.067。n=5 でのこの差はどちらの向きにもノイズの範囲で、「C に効果がない」ことを示したわけではない。

不採用を決めたのは**コスト側**であり、こちらは計測に依存しない。第二のインデックスは `/today` と `/wrapup` で同期し続ける必要があり、**同期が抜けたときに黙って古くなる**。古い wiki インデックスは「出典つきで自信を持って古い要約を答える」という、wiki-first が無い状態より悪い失敗の仕方をする。得られるかもしれない差が n=5 で判定できない程度である以上、この故障モードを引き受ける理由がない。

技術的な発見が2つある。

**1. コレクションを分ける方式はベクトル検索が壊れる。** qmd の `searchVec` は sqlite-vec が JOIN できない制約から、まず `vectors_vec` 全体からグローバルに上位 `limit * 3` 件を取り、**そのあとで `d.collection = ?` の post-filter をかける**実装になっている（`store.js` の `searchVec`）。169/1700 件しかない小さいコレクションは、グローバル上位に入れなかった時点で候補ごと消える。実測では `-n 5` で 0 件、`-n 100` にしてようやく 4 件返った。BM25 側は FTS が正しく絞るので無事だが、ハイブリッドの意味検索の半分が死ぬ。**小さいサブセットを別コレクションとして切るのは qmd では機能しない。**

**2. 独立インデックス（`qmd --index wiki`）なら正しく動く。** `vectors_vec` がそのインデックス専用になるためベクトル検索は正常。技術的には成立する方式であり、不採用の理由は上記の同期リスクだけである。

再検討する条件: vault が育って topical R@3 が 1.000 を割ったとき。そのときは天井が外れて計測で判定できるようになる。方式は独立インデックス（コレクション分割ではない）を使い、同期を `/today` と `/wrapup` の両方に組み込んだうえで、同期漏れを検出する手段もあわせて用意すること。

## 注意

- 問題数を増やすと `full` のリランキングが1問8〜13秒かかるぶんだけ線形に伸びます。15問で3〜4分
- `intent:` 行は入れていません。リランキングを使う経路でしかスコアに影響せず、バックエンド間の比較を濁すためです。`/vault-rag` 本番のクエリでは有効なので、実運用のクエリ設計とは意図的にずらしてあります
- vault の内容が変わると正解も変わります。ノートを消したりリネームしたら `verify-fixture.rb` が落ちるので、そこで気付けます
- **`exact` と `semantic` の正解は「その事実が現時点では wiki ではなく notes 側にしかない」という状態を固定したものです。** wiki が育って同じ事実を wiki ページが持つようになると、これらの質問で wiki ページが上位に来て「失敗」と集計されます。これらが落ち始めたら、劣化ではなく wiki が正当に引き継いだ可能性をまず疑い、そうなら `expected_files` を wiki ページへ更新してください
- このベンチは**検索品質しか測りません**。wiki の育ち具合（1回のingestで触るページ数、staleness、deferred の滞留）は `wiki-update/health/` の別の装置で測ります
